Seven common user journeys

1. Understand a package you received

Owner or project manager - Know what was delivered and what to ask next.

  1. 1
    Choose your goalStart > Understand the software
  2. 2
    Select your packageZIP > Analyze ZIP locally
  3. 3
    Read and inspectReview findings > Architecture > Evidence
  4. 4
    Agree next stepsCoverage > Save & next steps

Take away: Readable HTML report plus questions for the developer.

Boundary: A feature explanation is supported code evidence, not proof that the feature works.

2. Move a project between AI coding tools

Builder changing tools or developers - Continue from an evidence-backed handover, for example Claude to Codex.

  1. 1
    Save the sourceExport your authorized code package from the original tool
  2. 2
    Map the deliveryAnalyze > Architecture > Evidence
  3. 3
    Prepare the handoverHandover: setup clues, owners, gaps and next checks
  4. 4
    Continue elsewhereGive the next developer the code, reports and selected context

Take away: Original code package kept separately, plus one reviewed handover ZIP with reports and optional annotations.

Boundary: Manual handover. Reversium does not migrate conversations, agent memory, prompts, secrets or accounts.

3. Take over maintenance

Incoming developer or agency - Identify first files, required services and unresolved setup tasks.

  1. 1
    Analyze the deliveryStart > Prepare a developer handover
  2. 2
    Follow one featureArchitecture > Workflow > Evidence
  3. 3
    Review setup needsHandover > Setup clues; Coverage > Setup & readiness
  4. 4
    Assign and saveSet checklist owners; optionally include annotations in the handover pack

Take away: A scoped investigation and setup checklist for the exact delivery.

Boundary: Service references are clues. The developer still verifies versions, permissions, migrations and credentials.

4. Plan a change without guessing

Developer or maintainer - Find candidate components to inspect before editing.

  1. 1
    Pick the starting fileAnalyze > Change impact
  2. 2
    Explore connectionsUpstream and downstream candidate neighbors
  3. 3
    Check each claimArchitecture map > Evidence > Coverage
  4. 4
    Make and verify the changeUse your editor and normal tests; save a new baseline

Take away: Candidate impact notes and a source-backed test plan.

Boundary: Graph reachability is not proof that a component will be affected. Reversium does not edit or deploy code.

5. Check what changed in a new delivery

Owner, reviewer or developer - Compare a new package with a saved earlier analysis.

  1. 1
    Keep a baselineSave technical data (JSON) from the earlier analysis
  2. 2
    Analyze the new ZIPCreate a separate current report
  3. 3
    Compare reportsSelect earlier JSON; inspect files, findings and map changes
  4. 4
    Record the reviewCheck evidence; save comparison notes and next tests

Take away: Changed relationships and candidate effects, with disclosed omissions.

Boundary: Analyzer versions and packaging can change results. A difference is not automatically a defect.

6. Ask AI a focused question privately

Owner or developer needing an explanation - Share only selected evidence and check the answer.

  1. 1
    Choose the evidenceAI: select provider, question and up to 20 findings
  2. 2
    Review the exact textPrepare request; remove private details
  3. 3
    Choose how to submitOnline: manual handoff; local: eligible optional connection
  4. 4
    Check the answerMatch cited IDs/locations; record unsupported claims

Take away: A reviewed request and a human-checked explanation.

Boundary: Nothing is shared automatically. Online account-connected chat is disabled; provider terms/limits apply.

7. Verify behavior in a disposable local environment

Developer with an explicitly reviewed execution profile - Separate observed behavior from setup assumptions without touching live.

  1. 1
    Review support firstAnalyze package; review alerts and compatibility
  2. 2
    Prepare isolationLocal prerequisites, trusted assets and fresh isolation checks
  3. 3
    Run a bounded testFixed reviewed profile: real code, disposable data and accounts
  4. 4
    Record and stopCapture passes/blockers, stop guest and review matching evidence

Take away: Exact-package test record and separately recorded manual observations.

Boundary: Experimental local profile only, not any ZIP or a simulation. No production/live credentials. VM isolation cannot guarantee zero risk.
